Building an AI OSINT Agent: Architecture for Autonomous Investigation

MAY 2026 — AI ENGINEERING / OSINT / TOOL DEVELOPMENT / AUTOMATION

In previous articles I've shown the results of using AI agents for OSINT — profiling a USSS Most Wanted target, building complete intelligence profiles from a single username, and unmasking identity fraud structures from minimal seed data. This article covers what I haven't shown before: how the agent actually works — the architecture, the tool layer, the reasoning chain, and why this approach produces results that neither pure automation nor manual analysis can match alone.

This is not "asking ChatGPT to do OSINT." It's an autonomous agent with direct access to custom databases, enumeration tools, and correlation engines — capable of reasoning through an investigation the way an experienced analyst would, but at a speed and scale that no human can sustain.

The conceptual model is similar to what Palantir AIP does for government and enterprise clients: connect heterogeneous data sources through cloud infrastructure, then let an AI layer query, correlate, and reason across all of them simultaneously. Palantir charges millions for this capability. I built a focused version of the same architecture for OSINT — cloud-hosted databases (stealer logs, leaked records, enumeration results) unified under a single AI agent that can query any source, cross-reference findings in real time, and follow investigative threads across datasets that were never designed to talk to each other.

Why an Agent, Not a Script

The first question most people ask is: why not just write a Python script that queries your databases and correlates the results?

Scripts follow predefined logic. They're fast and reliable for known patterns, but they can't handle the unexpected pivots that make investigations productive. When a stealer log query returns an email that doesn't match the target name, a script either ignores it or follows a hardcoded fallback. An agent reasons about why there's a mismatch and decides to investigate the email owner independently — exactly what a human analyst would do.

The core insight is that OSINT investigations are decision trees with unknown branches. You can't script every possible pivot because you don't know what the data will reveal until you query it. An LLM agent handles this naturally — it evaluates results, formulates hypotheses, and selects the next query based on what it's learned so far.

The Tool Layer

Each tool is defined as a structured function that the agent can call with specific parameters. The agent sees a description of what each tool does and what parameters it accepts — it decides when and how to use them based on the investigation context.

tool definitions (simplified) 
tools = [
    {
        "name": "stealer_log_search",
        "description": "Search indexed stealer logs and breach data.
            Returns URLs, credentials, IPs, HWIDs, and timestamps
            for any matching email, username, or domain.",
        "parameters": {
            "query":      // email, username, or domain
            "query_type": // "email" | "username" | "domain" | "ip"
            "limit":      // max results (default 50)
        }
    },
    {
        "name": "leaked_db_search",
        "description": "Search leaked database records by name,
            CURP prefix, RFC, address, or date of birth.
            Returns identity records with full metadata.",
        "parameters": {
            "name":       // full or partial name
            "state":      // Mexican state code (optional)
            "curp":       // full or partial CURP
            "address":    // street, colony, or CP
        }
    },
    {
        "name": "enumerate_accounts",
        "description": "Check 40+ services for account existence.
            Returns confirmed accounts with leaked metadata
            (names, registration dates, profile fragments).",
        "parameters": {
            "identifier": // email, phone, or username
            "type":       // "email" | "phone" | "username"
        }
    },
    {
        "name": "curp_rfc_decode",
        "description": "Decode a CURP or RFC into its components:
            surname initials, birthdate, gender, birth state.
            Can cross-reference CURP ↔ RFC via shared prefix.",
        "parameters": {
            "identifier": // CURP (18 chars) or RFC (13 chars)
        }
    }
]

The tool definitions are intentionally descriptive. The agent needs to understand not just what a tool does, but when it's useful. A vague description like "search database" means the agent won't know whether to use it for a name, an email, or an IP address. Specificity in tool definitions directly translates to better investigation decisions.

Data Infrastructure: The Stealer Log Pipeline

The most critical data source is the stealer log database. Infostealers (RedLine, Raccoon, Vidar, Lumma) continuously produce credential dumps that circulate through Telegram channels. This data is ephemeral — channels get banned, files expire, links die. If you're not scraping and indexing it in real time, you lose it.

Agent Reasoning in Practice

This is where the architecture comes together. The agent doesn't follow a script — it reasons through the investigation, making decisions based on what each query returns. Here's a reconstructed reasoning chain from the identity fraud investigation:

agent reasoning chain — identity fraud case 
DIRECTIVE: "Investigate [target name]. Suspected financial
fraud. Build complete identity profile."

─── STEP 1: Initial pivot ───
REASONING: I have a name and a geographic area. No email,
no phone, no digital footprint. I'll start with stealer logs
— if this person has ever been compromised, their email will
be in the database.
CALL: stealer_log_search(query="[name]", type="username")
RESULT: 1 hit → email: ████████@hotmail.com

─── STEP 2: Anomaly detected ───
REASONING: The email doesn't match the target name. The
email domain contains a DIFFERENT name. This could mean
identity theft or a shared account. I need to investigate
both identities independently.
CALL: stealer_log_search(query="████████@hotmail.com", type="email")
RESULT: Platforms: MGM Resorts, Neiman Marcus, Epik...
→ luxury accounts inconsistent with reported income

─── STEP 3: Identity resolution ───
REASONING: The email owner appears to be a different person.
Let me search the leaked database for both names to see
which one has a real identity record.
CALL: leaked_db_search(name="[target]", state="target_state")
RESULT: 0 results — target identity DOES NOT EXIST

CALL: leaked_db_search(name="[email owner]", state="target_state")
RESULT: 1 result — CONFIRMED real person, DOB 1973,
CURP confirmed, registered address found

─── STEP 4: Hypothesis formed ───
REASONING: The target's operating name has zero records.
The email belongs to a confirmed real person. The target is
either using this person's email fraudulently, or IS this
person operating under a fabricated identity. I need to check
the RFC linked to the financial operations.
CALL: curp_rfc_decode(identifier="████770410██1")
RESULT: RFC decodes to: DOB April 10 1977 — does NOT match
either person. This RFC belongs to a THIRD individual.

─── STEP 5: Third party identified ───
CALL: leaked_db_search(curp_prefix="████770410")
RESULT: Match: [associate], DOB 1977-04-10, CDMX origin
→ RFC legally belongs to this person, NOT the target
→ Shared RFC = financial fraud structure (prestanombres)

─── STEP 6: Deceased identity detection ───
REASONING: The target name still has no records. The surname
combination is rare in Mexico. If I search for ANYONE with
this surname pair, I might find the source of the identity.
CALL: leaked_db_search(name="[surname combo]", state="all")
RESULT: 1 match: [elderly person], DOB 1930 — same rare
surname combination. Age 95. Likely deceased.
→ IDENTITY THEFT OF A DECEASED PERSON CONFIRMED

A script would have stopped at step 1: "name found in stealer logs, here's the email." The agent noticed the mismatch, investigated both identities, identified the RFC belonging to a third person, and searched for the rare surname that led to the deceased relative. Each step was a decision, not a predetermined action.

The Human-AI Collaboration Model

The agent is not a replacement for an analyst. It's a force multiplier that handles the mechanical correlation work while the human focuses on what AI can't do well:

division of labor 
AI AGENT EXCELS AT:
 [+] Cross-referencing identifiers across databases at scale
 [+] Detecting mismatches (email ≠ name, RFC ≠ owner)
 [+] Exhaustive enumeration (40+ services in seconds)
 [+] Pattern recognition across stealer log metadata
 [+] Family network reconstruction via naming conventions
 [+] Maintaining context across hundreds of data points

HUMAN ANALYST REQUIRED FOR:
 [+] IMINT / GEOINT (visual analysis, satellite imagery)
 [+] Judgment calls (is this identity theft or prestanombres?)
 [+] Legal and ethical boundaries (what CAN we query?)
 [+] Source validation (is this stealer log data reliable?)
 [+] Creative pivots (querying a car photo for geolocation)
 [+] Client communication and report writing

THE COLLABORATION:
 Analyst provides: seed data, scope, and judgment
 Agent provides: exhaustive correlation at machine speed
 Analyst reviews: validates findings, directs follow-up
 Agent executes: deeper queries based on analyst direction

In the full-spectrum OSINT investigation, the agent handled enumeration, stealer log correlation, and family network mapping autonomously. But the IMINT analysis — recognizing architectural style in a car photo, querying Overpass Turbo, and confirming via Google Earth satellite imagery — required human visual analysis and creative reasoning that no current AI handles reliably.

The ideal workflow is iterative: the agent produces an initial intelligence picture, the analyst reviews it and identifies gaps or anomalies worth pursuing, then directs the agent to dig deeper in specific directions. Each cycle compresses what would be hours of manual work into minutes.

Why This Approach Matters

The threat intelligence industry is moving toward AI-assisted analysis, but most implementations are superficial — chatbots that summarize reports, or RAG systems that retrieve relevant documents. Those are useful but limited.

What I've built is fundamentally different: an autonomous investigator with direct tool access to real intelligence databases. The agent doesn't summarize other people's findings — it generates its own by querying raw data sources and reasoning about the results. This is the difference between an AI that reads intelligence reports and an AI that produces them.

For organizations running OSINT at scale — threat intelligence firms, fraud investigation units, law enforcement agencies — the implications are significant:

  • Analyst capacity multiplied — one analyst with agent support can handle the throughput of a 5-person team for correlation-heavy work
  • Consistency — the agent checks every database, every time. Human analysts skip sources when pressed for time. The agent doesn't.
  • Discovery of non-obvious connections — the identity fraud case was cracked because the agent searched for a rare surname across all states. A human analyst under time pressure might not have made that query.
  • Institutional knowledge preservation — the investigation methodology is encoded in the tool definitions and agent prompts, not locked in a senior analyst's head
